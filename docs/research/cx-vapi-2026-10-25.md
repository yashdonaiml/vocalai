# Vapi customer activation: evidence and opportunities

Research date: October 25, 2026 (America/Chicago). Scenario: a nontechnical service-business owner wants an inbound agent to capture an enquiry, save it to the business system, and verify the saved result.

## Method and limits

Used `cx-competitive-research` and read the REA routing skill. This pass used official web documentation and current owned source. REA MCP was not available; no REA CLI was executed, no client configuration changed, and no native analysis engine was installed. Browser/authenticated product behavior was not newly exercised. `docs/competitor-vapi-audit-2026-10-24.md` supplied historical context only, not fresh execution evidence. No app code, accounts, calls, OAuth grants, payments, or production settings were changed. Only this research note was created.

Evidence labels: **D** = current official documentation; **S** = current owned source; **H** = dated historical observation; **I** = inference; **U** = unresolved. Read date does not establish when a vendor last changed its implementation. No times or click counts were measured.

## The strongest Vapi advantages for this customer

1. **A runnable starting point.** Presets and use-case templates reduce component selection before first value. The lesson is a supported default, not that every template is a fully connected business solution.
2. **Real native operations.** Google account authorization plus a typed append-row operation is materially different from telling an owner to build an HTTP receiver. Calendar similarly has availability/create operations. [Calendar guide](https://docs.vapi.ai/tools/google-calendar).
3. **Managed delivery and understandable diagnostics.** Number assignment and published-version semantics reduce hosting/telephony decisions; error categories make troubleshooting addressable. These are published contracts, not measured uptime or conversion advantages.

## Where we can improve on its documented experience

- **Eliminate copied IDs/ranges and separate tool assembly.** For “Save enquiries,” let an owner choose an account, spreadsheet and worksheet by name, preview the columns and finish. Generate the operation, input collection, mapping and draft attachment behind the scenes. If a new destination is created, show that explicit action and obtain its authorization.
- **Make the real result the test's finish line.** Show a receipt such as “Enquiry saved to Leads, row 42,” with a destination link, rather than ending at an HTTP response or transcript. Display failed, pending, and uncertain outcomes separately. Notification delivery is another status.
- **Expose one release decision.** Keep draft/version/promotion rules internally, but give an owner an assistant-specific checklist and one reviewed activation action. Do not require them to understand workspace model presets, tool versions or environments to use the supported pack.
- **Prevent incompatible combinations before setup progresses.** Vapi's current GPT-Live docs list compatibility restrictions: GoHighLevel is not supported there, native tool rejection settings differ, and uncertain writes are not blindly retried. This is a useful warning against claiming universal engine/tool compatibility. Our supported pack should select validated combinations and explain unavailable options before the test, not after a real caller asks for an action. [GPT-Live tools](https://docs.vapi.ai/gpt-live/tools).

Vapi still documents manual prompts/tool descriptions and resource-ID entry. That is a concrete improvement opportunity. It does not prove its entire current UI lacks assisted alternatives. Claims that we are already faster, more reliable, or safer would need direct comparative measurement.

## Current Vocallay source gaps and implementation slices

### V1 — P0: make the supported outcome executable in voice

- **Owner:** runtime + product engineering. **Dependencies:** an explicit supported task/language/preset matrix.
- **Source:** `src/lib/agent-config.ts:104-124` defaults agents to native realtime. `runtime/src/agent.ts:85-95` refuses confirmation-required actions outside composable English or the specific Telugu-English mode. `src/lib/integration-tasks.ts:14-43` defines lead/ticket writes. `src/lib/tools.functions.ts:76-131` approves a successful console test, which does not exercise voice confirmation.
- **Change:** one capability resolver used by task selection, managed preset choice, readiness and bundle compilation. Automatically choose a validated voice preset for the initial enquiry pack; block unsupported task/language/engine combinations early. Keep exact confirmation and current authorization checks.
- **Acceptance:** a real supported voice test collects/corrects details, completes exact caller confirmation, produces one persisted business record and receipt; a native/unsupported selection is explained before deployment. A declined or interrupted confirmation produces no external write.
- **Recovery/rollout:** frozen operation identity must remain stable through retry and uncertain writes. Release only for the validated matrix. Broader multilingual/native confirmation is outside this slice.

### V2 — P0: native destination setup for the first enquiry pack

- **Owner:** integration/backend + frontend. **Dependencies:** V1, provider app registration/approved scopes, pilot destination choice. Google Sheets is a practical first target if pilots use it; otherwise implement their actual CRM deeply rather than both shallowly.
- **Source:** `src/routes/_authenticated/tools.tsx:364` says app sign-in is unavailable; lines 434-437 require an endpoint path. `src/lib/integration-tasks.ts:52-83` supplies a fixed contract rather than provider mapping. `src/lib/tools/adapters/http.server.ts:13-54` executes general mappings.
- **Change:** provider authorization/refresh/revoke service with encrypted credentials; account and resource discovery; typed append/create operation; collection-field preview; destination mapping and receipt normalization. Reuse catalog revisions, approvals, Tool Gateway and audit records. Keep generic API/MCP under Advanced.
- **Acceptance:** a fresh supported user connects without copying API URLs, IDs or JSON. A synthetic test appears at the chosen destination with an inspectable record reference. Revoked authorization produces a reconnect action; refreshing credentials does not accidentally duplicate the business write. Wrong-tenant resources are rejected server-side.
- **Recovery/rollout:** do not auto-repeat a timed-out append without a provider-backed reconciliation/idempotency strategy. Start with a controlled pilot; no catalog-size claim and no automated campaign scope.

### V3 — P0: one resumable activation journey

- **Owner:** frontend + activation/backend. **Dependencies:** V1/V2 and validated telephony/payment readiness for the chosen market.
- **Source:** `src/routes/onboarding.tsx:207-215` ends at an unpublished draft. Integrations need a separate test authorization (tools page line 492), live approval (line 504), draft attachment (line 550) and external publish/deploy (line 556). `src/lib/platform.functions.ts` already coordinates bundle compilation and the atomic promotion RPC; reuse those boundaries.
- **Change:** persist assistant-scoped setup progress and readiness; one flow for business brief, destination selection, conversational test, receipt review and activation. Owner authorization should remain explicit for real tests, writes, payments and live deployment, but related review decisions can share a clear summary instead of several destinations.
- **Acceptance:** reload/reconnect resumes the correct step; one completed test is associated with the exact version/task contract; repeated activation cannot buy duplicate numbers. The owner gets a live/awaiting-provider/action-required state and a next step. External waiting time is displayed separately.
- **Recovery/rollout:** activation is staged/idempotent, not one transaction held across carrier/OAuth calls. No skipping eval/promotion gates, no hidden paid purchase and no promise of arbitrary-system minutes-to-live.

### V4 — P1: task-level receipt and recovery cards

- **Owner:** backend + frontend. **Dependencies:** V2 receipt contract.
- **Source:** `src/routes/_authenticated/conversations.$id.tsx:49-50,247` and `tools.tsx` show saved gateway outputs, mostly as JSON. `src/lib/events.server.ts` and gateway success events already distinguish execution from notification delivery.
- **Change:** normalize `outcome`, `recordId`, permitted destination URL, `operationId`, `syncState` and recoverable error into a task result; retain raw redacted output for Advanced/support. Keep separate notification state and ensure result links cannot expose a foreign tenant resource.
- **Acceptance:** owner can answer “Was the lead saved? Where? Was anybody notified? What should I do?” from one call card. Unknown writes remain unknown until reconciled; the system never equates a 2xx/queued response with a completed business operation.
- **Non-goals:** general workflow analytics builder, all CRM objects, re-implementing the gateway or automatic retries for arbitrary writes.

## Useful implementation distinctions

**Documented, not private-backend claims:** Vapi uses connected provider credentials, typed tools, assistant attachment and a published version lifecycle. Its docs explain response correlation and recommend idempotent service operations. They do not establish its database schema, token-vault implementation or transaction guarantees.

**Inference for our design:** retain the gateway as the execution policy boundary, add a small provider-native adapter layer and an assistant activation coordinator above it. The owner should choose a business destination and expected outcome; internal services should resolve operation names, resource IDs and bindings.

**Do not copy breadth prematurely:** more model presets, squads, provider knobs, visual flows or MCP catalogs will not resolve the current native-voice/write incompatibility or endpoint requirement. Hide advanced controls but keep the existing tenant isolation, versioning and confirmation safeguards.

## Evidence caveats and skill feedback

- Current Vapi Google documentation describes authorization flows; the current GoHighLevel guide describes API-key setup. Previous reports must not normalize every connector to OAuth. This illustrates why provider/account/version specificity matters.
- The general Function troubleshooting guide describes async result handling differently from GPT-Live's tool guide. These may be engine-specific contracts; no cross-mode behavior should be inferred without an engine-specific test. Our result taxonomy should distinguish accepted/queued/completed and explicitly name tested runtime modes.
- The new skill worked without blocking ambiguity. A useful narrow addition would be: when two official docs disagree, retain both URLs and the engine/API-version context; do not silently choose the easier claim. Evidence freshness alone cannot resolve different runtime contracts.

Critical path contributed to the unified plan: **compatible voice task → native destination → test receipt → resumable activation → recovery cards**. Proposed timing goals need nontechnical pilot measurement; none were measured here.
