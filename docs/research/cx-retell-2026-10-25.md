# Retell: customer activation research

Date: October 25, 2026, America/Chicago. Research owner: cx_retell. Customer experience is P0. Common task: a nontechnical service-business owner creates an inbound enquiry agent, connects a destination, tests it, activates it and finds a saved lead receipt.

## Method and limits

Applied `cx-competitive-research` and read upstream `reverse-engineer-anything`. This pass used current official documentation and current owned source. REA MCP was unavailable and the supplied host Node version was below the current REA requirement; no REA execution, installation or client repair was performed. Documentation/source fallback is sufficient for the claims below, not for reverse engineering a private service.

The coordinator additionally inspected the already-open Retell draft today, without running a call, editing, publishing or purchasing. These narrow fresh UI observations are marked **Observed/coordinator**. `docs/competitor-retell-dashboard-audit-2026-10-25.md` supplies historical UI evidence; its earlier configuration estimates and empty inventories are not new performance measurements. No OAuth grant, paid request, external message or probe was made. There is no measured activation time or live integration-success benchmark in this note.

## Three strongest activation advantages

1. **Working conversation before infrastructure.** The published quickstart separates a draft browser test from phone-number purchase. For our customer, the first success should be hearing an agent correctly handle an enquiry. The quoted “15 minutes” is a vendor journey claim, not our measurement. [Quickstart](https://docs.retellai.com/get-started/quick-start).
2. **A connected business system is more than an HTTP destination.** Provider operations and reusable account selection remove application-specific request construction. This is the gap in our current generic tasks. [Integration overview](https://docs.retellai.com/integrations/overview).
3. **Assistance remains attached to context.** Conductor supports context-aware help, proposed edits for review and guided walkthroughs. Our smaller implementation can start with deterministic next-step guidance and targeted draft assistance rather than reproducing a general dashboard copilot. [Conductor](https://docs.retellai.com/conductor/overview).

## Friction we can improve

Retell does not provide universal one-click OAuth. Its HubSpot setup requires a private app token and Super Admin work. The guide notes a connection read check can succeed while other operation scopes remain missing. A small provider-specific capability check can outperform a generic green “connected” status: “Read contacts works; saving leads needs this permission.” [HubSpot setup](https://docs.retellai.com/integrations/hubspot).

The integration catalog also includes API-key and tenant-ID/URL inputs alongside OAuth providers. Typed tools still need input/output setup. Our improvement is to assemble the exact enquiry pack, collect only its unresolved business choices and show a destination preview. [Integration overview](https://docs.retellai.com/integrations/overview).

CRM sync has four separately configured parts and creation of new CRM contacts is off by default. This is powerful but creates a mismatch risk for the owner who expects “save my leads” after merely connecting an account. We should ask explicitly whether the agent may create or update a lead and present the resulting record in the test. Full bidirectional sync need not be on the first critical path. [CRM overview](https://docs.retellai.com/integrations/crm-overview).

Retell documents pre-call processing that can delay the opening and continue later, plus bounded post-call work. We should keep initial caller context fast, allow a graceful fallback, and show unfinished post-call work as pending rather than reporting it delivered. This is a design recommendation, not a claim that our timing is already better. [Agent workflow](https://docs.retellai.com/agent/agent-workflow).

## Documented implementation pattern, not private backend reconstruction

The supported pattern is account connection → typed provider operation → fixed or conversation-filled inputs → filtered result/context variables → pre/during/post-call execution → logged outcome. We can build this independently as adapters behind our existing Tool Gateway. Public material does not reveal Retell's databases, token-vault internals, model scheduling, internal retries or reliability.

For lead capture, prefer one provider account with verified create/update rights and a narrow receipt contract. Draft configuration should carry destination and collection policy; immutable publication pins the mapping. A successful conversation, a queued request, a provider-created record and a staff notification are distinct outcomes.

## Current Vocallay source findings

These source locations were refreshed in this pass; they are not inferred from the old audit:

- `src/routes/onboarding.tsx:108` (`finishSetup`) and its completion view near line 207 stop at an unpublished draft. Business setup is not connected to the whole activation journey.
- `src/routes/_authenticated/tools.tsx:278` (`IntegrationSetup`) provides task selection, but line 364 explicitly excludes app sign-in, line 434 asks for an endpoint path, and line 556 sends the owner elsewhere to publish/deploy.
- `src/lib/integration-tasks.ts` generates three fixed HTTP schemas. Lead capture requires email as well as phone. A phone-only enquiry needs an explicit pack collection policy rather than a blanket requirement inherited from a technical contract.
- `src/lib/tools.functions.ts:39` (`requireIntegrationTest`) checks recent real console evidence; `approveIntegration` and `reviewTool` preserve meaningful gates. Keep them, but the guided interface should make a safe real test understandable and route the approval naturally.
- `src/lib/agent-config.ts:104` selects native realtime by default. `runtime/src/agent.ts:85-95` refuses confirmation-required execution outside supported composable English/Telugu-English configurations. Thus our default agent cannot complete the enquiry-write pack merely because the console HTTP test passed.
- `src/lib/evals.server.ts:17-25` runs only composable text regression; this is not proof of voice or integration correctness. Native gating needs a supported runner path before the launch flow can promise readiness.
- `src/components/app-shell.tsx:79-115` separates build/deploy/operate/manage surfaces. These can remain advanced pages while one assistant activation surface coordinates them.
- `src/components/managed-inbound.tsx:302,432` already has number connection and saved-call verification controls. Reuse those services instead of creating a second telephony implementation.

## Skill forward-test feedback

The skill correctly separated documented contracts from execution and avoided unnecessary REA setup for owned source. One practical improvement for the shared rubric: “connect an application” should explicitly classify **OAuth, copied API token, admin-created app, account URL/ID and partner approval** separately. A native logo is not evidence of zero-technical setup. This distinction materially changed the Retell comparison.

No consolidated roadmap is written here; the coordinator owns synthesis. First dependency is R-01, then a narrow R-02/R-03/R-04 slice. Defer catalog breadth, full CRM sync, arbitrary visual automation and a general-purpose copilot until nontechnical owners complete the supported enquiry journey. No completion-time or superiority claim has been measured.
